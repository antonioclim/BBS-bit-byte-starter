What we will learn

  • Construct and check even parity for a data string.
  • Demonstrate the limit of simple parity with a counterexample.
  • Encode four data bits in Hamming (7,4) under an explicit convention.
  • Calculate a syndrome, correct one flip and verify recovery.
  • Explain why a single-error decoder can miscorrect two errors.
  • Construct and check a teaching CRC through XOR polynomial division.
  • Distinguish a passed check from proof of data identity or authenticity.

Why this will help

  • Understand what a check can detect or repair and which assumptions must be stated.
  • Select tests that check the method and its limits rather than confirming only favourable examples.
  • Check an explanation received from Gemini without treating it as an authority.

What to retain after the steps fade

  • Declare parity, position order, width and generator first.
  • Simple parity detects an odd number of flips; it does not locate them.
  • Hamming (7,4) corrects one flip under that assumption; two can induce miscorrection.
  • Our teaching CRC uses XOR: append r zeroes during construction and check the complete codeword at reception.
  • Zero remainder shows that the code relation holds, rather than guaranteeing original or authentic data.
  • Prediction, independent calculation, test and bounded conclusion remain useful after the details are forgotten.

The core route uses even parity, Hamming (7,4) and a CRC example using binary division. Hamming positions are numbered from the left, starting at 1. Hamming (12,8) and SECDED (8,4) are supplements. Results depend on the convention and assumed error bound.

01 · Learning minutes · 0–7 min

S03 · How do we know that a bit has changed?

A check can report an error without identifying its position. Correction needs extra information and an explicit assumption about the errors that can occur.

Why this method works

A transmitted file, a value in memory or a message in a project can differ from its original. Today we build three small checks to understand what they establish and where their guarantees end.

Steps to follow

  1. Read the convention and the original message before selecting a formula.
  2. Predict the result, calculate on paper and verify it with a second calculation.
  3. Use the tool after predicting. Within the 90-minute meeting we reserve 10 minutes for Q03 and 80 for explanation, practice and review; supplements are for separate reference.
One problem, three responses

A single parity bit detects an odd number of changed bits. Hamming (7,4) can locate and correct one change under the stated assumptions. A CRC checks whether a bit string satisfies a divisibility relation: it does not automatically identify the error position.

By the end you will be able to construct these checks, introduce an error deliberately and explain a misleading result. Answers in this lesson receive local feedback: they are not sent to Moodle and do not award seminar marks.

What we need and where confusion can arise

We need to read a bit string, count its 1s and apply XOR to a pair of bits. Before continuing, predict the count of 1s in 0101 and the result of 1 XOR 1.

Hint and starting check

Count the positions containing 1: there are two. XOR returns 1 for different bits and 0 for equal bits, so 1 XOR 1 = 0. If this is unclear, work through two pairs in the XOR example, then return here.

The likely difficulty is a change in meaning: a bit position, a syndrome value and a CRC remainder are different objects. Label each number with the kind of result it represents.

A mistake to avoid: “The check passed” does not establish that the received message equals its original.

In S05–S07 we will turn such explanations into requirements, tests and changes recorded in Git.

02 · Learning minutes · 0–7 min

What counts as an error in this seminar?

A bit error changes 0 to 1 or 1 to 0. We preserve message length and positions; a lost or inserted bit would require a different model.

Why this method works

Without a stated model we may ask an algorithm to solve a problem it was not designed for. Here we can compare strings position by position and count the changes.

Steps to follow

  1. Record the original and received strings separately, with equal lengths.
  2. Mark the positions that differ; each difference is a bit flip.
  3. Check the received string using the code rules, without pretending that the receiver knows the original.
Only our experiment has the original available

Start with 10110011. Flipping the rightmost bit gives 10110010: one flip. Flipping the first two positions gives 01110011: two flips. The number of 1s can increase, decrease or stay unchanged.

In an experiment we know the original and can measure the errors. At a real receiver we usually have only the received string and its check information. We must therefore interpret a check without assuming access to the original.

Try before opening the answer

Hint 1

Compare positions from the left rather than counting each string’s 1s separately.

Hint 2

Mark only columns containing two different digits.

Answer and verification

2

The first two positions differ; the remaining six are identical.

A mistake to avoid: An error does not necessarily add a 1: a change from 1 to 0 is also an error.

Project tests will state what we change and what we expect before running the program.

03 · Learning minutes · 7–19 min

Construct even parity

Choose an extra bit so that the total number of 1s, including that bit, is even. In this lesson we append it to the right of the data.

Why this method works

Parity provides a simple check that we can calculate without a program. It separates data from check information and will return in the individual requirement in S07.

Steps to follow

  1. Count the 1s in the data, rather than the decimal value of the byte.
  2. For an odd count the parity bit is 1; for an even count it is 0.
  3. Append the bit on the right and count the 1s in the entire string again.
The data 10110011 receive a parity bit of 1

10110011 contains five 1s. Choose p = 1, so the transmitted string is 101100111. It contains six 1s, an even number. The data contain eight bits but the protected string contains nine: the extra bit is not part of the byte value.

Quick checks: 00000000 receives 0 and 11111111 also receives 0. Both data strings already contain an even number of 1s. Odd parity would use a different rule; we do not combine it with this one.

Try before opening the answer

Which even-parity bit do we append to the right of 10110011? Enter 0 or 1.

Hint 1

Count the 1s in the eight data bits first.

Hint 2

Choose the bit that makes the total count of 1s even.

Answer and verification

1

Five 1s in the data plus a parity bit of 1 give six 1s in total.

A mistake to avoid: “Even parity” concerns the count of 1s in the complete string, rather than whether its numerical value is even.

In S07 we will apply even or odd parity according to the assigned variant and check the result for the eight data bits.

04 · Learning minutes · 7–19 min

Check the received string

At the receiver calculate parity over the entire string, including the extra bit. An odd number of 1s violates the agreed rule.

Why this method works

The receiver cannot simply calculate a replacement parity bit and declare the message correct. It must check the received information against the relation that should have held at transmission.

Steps to follow

  1. Keep the received parity bit; do not replace it.
  2. Count the 1s in the complete string or XOR all its bits.
  3. A result of 0 means that the parity relation holds; a result of 1 signals a violation.
An error in the data or check bit is reported

The correct string 101100111 has parity 0. Flipping the last position produces 101100110, with five 1s: the check returns 1. Flipping the first bit of the correct string produces 001100111, again with five 1s: the check also returns 1.

In both cases we observe an inconsistency but cannot identify the changed position. One result of 1 cannot select among nine possible positions. We can request retransmission or use a correction mechanism; we do not guess the bit.

Try before opening the answer

What is the XOR of all bits in 101100110? Enter 0 or 1.

Hint 1

Keep all nine positions, including the received check bit.

Hint 2

XOR of all bits depends on whether the count of 1s is odd or even.

Answer and verification

1

Five 1s give XOR 1, so the even-parity relation is violated.

If a single flip produces no alarm

Symptom: you obtain XOR 0 for 101100110. Possible cause: you recalculated and replaced the received check bit or omitted a position. Intermediate check: keep all nine positions and count the five 1s separately. Minimum correction: repeat XOR over the received string, keeping its check bit. Recheck: original string 101100111 gives 0 and the single-flip string gives 1.

A mistake to avoid: Do not remove the check bit before checking the relation and do not interpret an alarm as an error position.

In a project a check result needs a clear meaning: valid, invalid or undecidable.

05 · Learning minutes · 7–19 min

Two changes can pass the check

Simple parity detects any odd number of bit flips. Any even number of flips preserves parity and passes this check.

Why this method works

Testing only one error can create false confidence in a program. A counterexample establishes the precise limit of the method, even when its implementation has no defect.

Steps to follow

  1. Start with a string that satisfies even parity.
  2. Flip two different positions and preserve every other position.
  3. Recalculate the check, then compare the string with the original available in the experiment.
The check passes but the data have changed

Flip the first two positions of 101100111 to obtain 011100111. There are still six 1s, so the check returns 0. However, the received data are 01110011, different from 10110011.

Each flip changes parity once; two flips change it twice and restore its initial value. We do not say that “parity detects at most one error”: three flips are also detected. The precise statement is that it detects an odd number of flips and does not detect an even number.

Hint 1

Hint 2

Answer and verification

Two flips preserve parity. The string has changed but the simple check passes.

Try a case of your own

Choose a different eight-bit string from 10110011. Predict the parity bit, construct the protected string and choose two distinct data positions to flip. Record the XOR prediction before calculating. Compare the data too: a passed check with changed data refutes “parity detects every modification”. Explain why you chose two positions.

These cases replace repetition of an example within the existing discussion; they are not new homework and receive no separate grade. Keep your attempt on paper for review.

A mistake to avoid: Do not extend success for one flip to every type of error.

06 · Learning minutes · 19–42 min

Hamming: more checks identify a position

Hamming (7,4) uses four data bits and three check bits. The three checks form a syndrome that identifies the position of a single bit flip.

We move from byte 10110011 to the four data bits 1011 because Hamming (7,4) reserves exactly four data positions. We keep the problem of receiving errors but change the message and check information to make single-error location visible.

Why this method works

Simple parity gives only an alarm. Checks covering different groups can produce a distinct combination for each position and indicate which bit to change.

Steps to follow

  1. Separate the four data bits from the seven codeword positions.
  2. Declare even parity and position order before inserting any bits.
  3. Use correction decoding only under the assumption of at most one flip across the seven positions.
Why are three check bits enough?

Three binary results allow eight combinations: one for “no violated checks” and seven for the seven possible positions of a single error. This count explains the size but does not replace constructing the check groups.

The notation (7,4) gives the total length and number of data bits, in that order. It does not mean seven data bits plus four check bits. We will encode 1011, introduce one flip and verify recovery of the data.

More generally, for m data bits and r checks, locating one error requires 2ʳ ≥ m + r + 1: one state per position and one for no error. For m = 4, r = 2 is insufficient because 4 < 7; r = 3 meets the bound, 8 = 8. This is necessary, rather than proof that arbitrary check groups form a correct code.

Try before opening the answer

How many extra bits does Hamming (7,4) contain? Enter a decimal integer.

Hint 1

Hint 2

Extra bits occupy positions that do not hold data.

Answer and verification

3

The total length is 7 and there are 4 data bits; the difference is 3.

A mistake to avoid: A syndrome does not promise correction of an unlimited number of errors.

A software requirement must also state the conditions under which its result can be used.

Hamming positions: number from the left

In this lesson positions are 1, 2, …, 7 from left to right. Positions 1, 2 and 4 are check positions; 3, 5, 6 and 7 receive the data in their original order.

Why this method works

Some materials number from the right or display bits in another order. The same code name does not remove these differences; a written convention lets us verify without guessing.

Steps to follow

  1. Write a row of position numbers first.
  2. Reserve the powers of two: 1, 2 and 4.
  3. Insert data bits 1, 0, 1 and 1 in the remaining positions: 3, 5, 6 and 7.

08 · Learning minutes · 19–42 min

Check groups follow from position numbers

Check p1 covers 1, 3, 5 and 7; p2 covers 2, 3, 6 and 7; p4 covers 4, 5, 6 and 7. Each group, including its own check bit, must have even parity.

Why this method works

The groups are not arbitrary lists. A position’s binary representation shows which checks include it and explains why the syndrome can identify that position.

Steps to follow

  1. Write position numbers as three bits: 001, 010, …, 111.
  2. Group p1 includes numbers ending in 1; p2 includes those with the weight-2 bit set; p4 includes those with the weight-4 bit set.
  3. Calculate XOR for each group; during encoding choose the check bit so that the XOR of the complete group is 0.
Position 6 has the signature 110

Position 6 is 110₂: it belongs to p2 and p4 but not p1. A single flip at position 6 therefore changes exactly those two checks. Position 7, 111₂, belongs to all three.

XOR returns 1 for an odd number of 1s and 0 for an even number. To calculate p1, use data positions 3, 5 and 7: 1 XOR 0 XOR 1 = 0, so p1 = 0. The check including p1 also returns 0.

09 · Learning minutes · 19–42 min

Encode the data 1011 completely

After placing the data, calculate p1, p2 and p4 separately, then check every group again. Under our convention the result is 0110011.

Why this method works

Checking after encoding can reveal a wrong parity value or a bit in the wrong position. A result copied from a tool does not replace these steps.

Steps to follow

  1. Place data 1, 0, 1 and 1 at positions 3, 5, 6 and 7.
  2. Calculate p1 from 3, 5 and 7; p2 from 3, 6 and 7; p4 from 5, 6 and 7.
  3. Write all seven positions in order, recalculate the three checks and extract the data.

10 · Learning minutes · 19–42 min

Calculate the syndrome from the received string

Let s1, s2 and s4 be the XOR results for the received groups. The numerical syndrome is s1 + 2s2 + 4s4; its binary representation is s4s2s1.

Why this method works

The order must be stated. Writing s1s2s4 and reading it as an ordinary binary number can identify another position even when all three checks are correct.

Steps to follow

  1. Receive the string without changing any bit first.
  2. Calculate the three XOR results, each including its check bit.
  3. Combine them with weights 1, 2 and 4; under the single-error assumption the result identifies the flipped position.
Receive 0110001

Compared with our codeword 0110011, position 6 has been flipped. For received string 0110001, group p1 gives 0 XOR 1 XOR 0 XOR 1 = 0. Group p2 gives 1 XOR 1 XOR 0 XOR 1 = 1. Group p4 gives 0 XOR 0 XOR 0 XOR 1 = 1.

Thus s1 = 0, s2 = 1 and s4 = 1. The syndrome is 0 + 2 + 4 = 6, or 110₂ in s4s2s1 order. This calculation uses only the received string; the original serves later as an experimental check.

Answer and verification

s1 = 0, s2 = 1 and s4 = 1; their weighted sum is 6.

If the syndrome is 3 rather than 6

Symptom: you obtain 3 for 0110001. Possible cause: you read s1s2s4 as a binary number. Intermediate check: calculate s1 = 0, s2 = 1, s4 = 1 separately; if these differ, revisit the relevant group. Minimum correction: use weights s1 + 2s2 + 4s4. Recheck: the syndrome is 6; flipping position 6 restores 0110011, with syndrome 0 and data 1011.

A mistake to avoid: Do not concatenate s1s2s4 and interpret it using ordinary left-to-right weights.

11 · Learning minutes · 19–42 min

Correct one flip and check again

Under the assumption of at most one error, a nonzero syndrome identifies the bit to flip. After changing it, check every group and only then extract the data.

Why this method works

Correction does not end with a modification. Rechecking confirms that the result is a codeword; comparison with the original in our experiment confirms recovery.

Steps to follow

  1. For 0110001, syndrome 6 identifies position 6 from the left.
  2. Flip only that bit: 0 becomes 1, producing 0110011.
  3. Recalculate the syndrome, now 0, and extract positions 3, 5, 6 and 7: 1011.
A check bit can also be wrong

Flipping position 2 of 0110011 produces 0010011. Only check p2 is violated, so the syndrome is 2. Correct position 2 rather than one of the data bits. The procedure covers any single flip across the seven positions.

With syndrome 0 we change no bit and report that the checks hold. If multiple errors are possible, this result does not establish that the message equals its original.

12 · Learning minutes · 19–42 min

Two errors: an alarm does not justify correction

Hamming (7,4) has minimum distance 3. It can detect any two flips when used for detection only, but a decoder that automatically corrects one error can miscorrect two.

Why this method works

“Detects two” and “corrects one” do not mean that the decoder automatically distinguishes those cases. One error and two errors can produce the same syndrome; extra information is needed to distinguish them.

Steps to follow

  1. Flip positions 1 and 2 in 0110011 to obtain 1010011.
  2. Calculate the syndrome: 1 XOR 2 = 3; checks s1 and s2 are violated.
  3. Show what happens if the decoder assumes one error and flips position 3, then compare the data with the original.
A valid but wrong result

The distance between two strings counts differing positions. Minimum distance 3 means that any two distinct valid codewords differ in at least three positions.

1010011 has syndrome 3. Automatic correction at position 3 produces 1000011, whose syndrome is 0. Its extracted data are 0011, different from the original 1011. We have not repaired the two errors: we have introduced a third and reached another valid codeword.

For detection without correction, the nonzero syndrome would provide an alarm. To correct one error and reliably distinguish two, an extension such as SECDED is needed, as explained separately. Its guarantees are also bounded.

13 · Learning minutes · 42–63 min

CRC: calculate with XOR, without carry or borrow

In our teaching CRC, binary coefficient addition and subtraction are both XOR: 0 with 0 gives 0, 0 with 1 gives 1, 1 with 0 gives 1 and 1 with 1 gives 0.

For CRC we choose data 1101 and generator 1011 so that every division alignment fits in a small table. This is a new case, rather than a continuation of the Hamming codeword. We retain the same question: what conclusion does the received check support?

Why this method works

The layout resembles long division but the calculation does not use ordinary integer arithmetic. A carry or borrow would change the algorithm.

Steps to follow

  1. Align the strings at the same positions.
  2. Apply XOR independently to each bit pair; nothing propagates to a neighbouring position.
  3. During division, apply the aligned generator when the current bit is 1; when it is 0 move to the next position.
The first operation in our example

1101 XOR 1011 = 0110. The four calculations are 1 XOR 1 = 0, 1 XOR 0 = 1, 0 XOR 1 = 1 and 1 XOR 1 = 0. We do not read this as “13 minus 11”.

For the longer string 1101000, generator 1011 aligned at the left becomes 1011000. XOR produces 0110000. The leading zero shows that we have removed the highest-degree term of the current step.

Try before opening the answer

Enter 1101 XOR 1011 as four bits, without spaces.

Hint 1

Hint 2

Equal pairs give 0 and different pairs give 1.

Answer and verification

0110

Apply XOR independently to all four pairs, without borrowing.

A mistake to avoid: XOR is not subtraction of the decimal values represented by the strings.

A small manual example is useful for checking an algorithm before trying longer cases.

14 · Learning minutes · 42–63 min

Declare the CRC convention before calculating

Read from the left: the first bit is the highest-degree coefficient. Generator 1011 represents x³ + x + 1, has degree r = 3 and produces a remainder of exactly three bits.

Why this method works

A label such as “CRC” does not specify a complete algorithm. We use direct polynomial division with a zero initial value, no bit reflection and no final XOR.

Steps to follow

  1. Write message M = 1101 and generator G = 1011.
  2. Determine r: the generator has four coefficients and degree 3.
  3. Append r zeroes to the message and keep the remainder on r positions, including leading zeroes.
Why append three zeroes?

Message 1101 represents x³ + x² + 1. Appending 000 gives 1101000, multiplying the message polynomial by x³. This reserves three positions on the right for check information.

The remainder has degree below 3 but we display it using exactly three bits. The polynomial remainder 1 is written 001, rather than just 1. This width makes construction and reading of the transmitted codeword unambiguous.

A mistake to avoid: Do not confuse the generator’s four bits with the remainder’s three bits.

If you stop with remainder 010

Symptom: you declare remainder 010 at intermediate string 0001010. Possible cause: you stopped division too early. Intermediate check: the first 1 is at position 4 from the left, so the four-bit generator still fits. Minimum correction: apply the final XOR with 0001011. Recheck: obtain 0000001, giving remainder 001; codeword 1101001 then gives remainder 000.

A mistake to avoid: Do not stop after the first XOR or add the remainder using integer arithmetic.

In a project a table of steps may provide better evidence than a screenshot of the final answer.

16 · Learning minutes · 42–63 min

At the receiver divide the complete codeword

The receiver divides the data together with their CRC bits by the same generator. It does not append zeroes again. A nonzero remainder reports that the received string violates the code relation.

Why this method works

Appending zeroes belongs to constructing check information from data. Repeating that step at reception would check a different polynomial and could change the interpretation of the result.

Steps to follow

  1. Receive all seven positions of the codeword.
  2. Apply the same XOR division with generator 1011.
  3. Keep three remainder bits: 000 means the check relation holds; any other remainder means a violation.
Two received strings, two results

1101001 divided by 1011 gives remainder 000. Flipping the rightmost bit produces 1101000, with remainder 001. The error is detected even though it affects a check position.

Remainder 001 is not, by definition, the number of the wrong position. In this seminar CRC is used for detection; we do not apply the Hamming correction rule. A nonzero result may lead to rejection or retransmission, depending on the protocol.

Try before opening the answer

For received string 1101001, what remainder does generator 1011 produce? Enter three bits.

Hint 1

Divide the complete codeword without appending more zeroes.

Hint 2

Check whether this codeword satisfies the relation built at transmission.

Answer and verification

000

The constructed codeword is divisible by the generator; no zeroes are appended at reception.

A mistake to avoid: Do not treat a CRC remainder as a Hamming syndrome that automatically identifies the error position.

The same label, “check”, can conceal results with different meanings; an API must distinguish them.

17 · Learning minutes · 42–63 min

A CRC can pass for different data

A change is undetected when its error polynomial is divisible by the generator. Zero remainder is a code condition, rather than proof that the data are original or that the sender is authentic.

Why this method works

Accidental-error detection does not replace authentication. We can construct an exact counterexample without probabilistic estimates or declaring the method useless.

Steps to follow

  1. Start with valid codeword 1101001.
  2. XOR it with error mask 0001011, the generator aligned at the right.
  3. Divide the result 1100010 by 1011; observe its zero remainder and changed data.
Three flips invisible to this check

1101001 XOR 0001011 = 1100010. The mask changes three positions and is itself divisible by 1011. Both codewords give remainder 000 but their data are 1101 and 1100 respectively.

This does not claim that all three-error patterns pass. It demonstrates one undetected error for the selected generator and length. In practice generators and parameters are chosen against precise requirements; deliberate modification requires appropriate security mechanisms rather than an invented CRC guarantee.

Answer and verification

000

It is another string divisible by the generator, with different data. Zero remainder establishes only that the CRC check relation holds.

Try a case of your own

Choose four data bits different from 1101 and keep generator 1011. Construct the seven-bit codeword and predict the remainder after XOR with mask 0001011. Check the remainder and the first four data bits. Changed data with zero remainder refute “a passed CRC establishes original data”. Justify the mask through divisibility rather than its count of flipped bits.

A mistake to avoid: Do not say “valid CRC, therefore a secure file” or attribute authentication guarantees to a CRC.

Supplement · SECDED: one extra overall parity bit

Appending an overall parity bit to Hamming (7,4) gives the extended (8,4) code with minimum distance 4. Assuming at most two flips, it can correct one and report two without correcting them.

Why this method works

Overall parity distinguishes cases with the same Hamming syndrome. This rule cannot be used for ordinary Hamming without the extra bit.

Steps to follow

  1. Keep the first seven positions as in the lesson and append p0 on the right.
  2. Check syndrome s over the first seven positions and XOR t over all eight.
  3. Use the table only under an at-most-two-flips model; recheck after any correction.
Codeword 01100110 and the decoder rules

0110011 contains four 1s, so p0 = 0 and the extended codeword is 01100110.

Supplement · Hamming distance explains guarantees

The Hamming distance between equal-length strings is the number of differing positions. A code’s minimum distance is the smallest distance between two distinct valid codewords.

Why this method works

Valid codewords sufficiently far apart allow a bounded number of changes to be noticed or corrected. This explains how adding redundancy can improve a check.

Steps to follow

  1. Compare positions rather than the difference between numerical values.
  2. A code with minimum distance d guarantees detection of up to d − 1 flips.
  3. Guaranteed correction covers t flips when 2t + 1 ≤ d. These are distinct guarantees; the decoding policy must select the appropriate action.
Why does ordinary Hamming not automatically distinguish two errors?

In Hamming (7,4), codewords 0110011 and 1000011 differ in their first three positions: their distance is 3. String 1010011 is at distance 2 from the first and distance 1 from the second. A nearest-codeword decoder selects the second even though our experiment identifies the first as the transmitted word.

The code has d = 3: it guarantees detection of two flips without correction, and correction of one when at most one is assumed. The extended code has d = 4 and permits the SECDED policy explained in its separate supplement.

For correction of up to t flips, a necessary condition is 2ʳ ≥ Σᵢ₌₀ᵗ C(n,i), where n is total length and r = n − k. With n = 63, k = 57 and t = 2 this would require 64 ≥ 1 + 63 + 1953 = 2017, which is false: six check bits cannot guarantee such correction. Satisfying this count would still not replace construction and checking the code distance.

Try before opening the answer

What is the Hamming distance between 0110011 and 1000011?

Answer and verification

3

Positions 1,2,3 differ; all other positions are identical.

A mistake to avoid: Minimum distance belongs to the set of valid codewords, rather than to one selected message.

The mathematical guarantee and program policy must be explained together.

Supplement · What is a burst error?

Burst length is measured from the first flipped bit to the last, inclusive; interior positions may be flipped or unchanged. It is not simply the count of flipped bits.

Why this method works

Nearby transmission errors can form a burst. A guarantee about burst length must be read with this definition rather than replaced by a claim about any group of errors.

Steps to follow

  1. Describe the error with a mask: 1 marks a flipped position and 0 an unchanged position.
  2. Find the first and last 1 and measure the inclusive span.
  3. For the direct division used here, a degree-r generator with constant term 1 detects every burst of length at most r.
Generator 1011, degree 3

Mask 0000101 flips two bits but has burst length 3. With G = 1011 its remainder is 101, nonzero, so the error is detected. Mask 0001011 flips three bits and has length 4; being the aligned generator itself, it is undetected.

The guarantee follows because, after removing zeroes outside the burst, the error polynomial has degree below r. A generator with constant term 1 cannot divide the shift factor, and a nonzero lower-degree polynomial cannot be its multiple. Do not extend the guarantee to longer bursts without further analysis.

Try before opening the answer

What is the burst length of mask 0000101? Enter a decimal integer.

Answer and verification

3

The span from the first 1 to the last includes three positions even though only two are flipped.

A mistake to avoid: “Burst length 3” does not require all three positions to be flipped.

A precise definition changes which test cases are needed to check a guarantee.

Supplement · Why can two CRC calculators disagree?

A CRC profile specifies more than a polynomial: width, initial value, bit order and possible reflection, final transformation and serialisation rules. The algorithm convention must also be read.

Why this method works

A different result from an online calculator does not automatically refute teaching division. It may compute another profile or interpret “1101” as four characters rather than four bits.

Steps to follow

  1. Check whether input means a bit string, a hexadecimal number or the bytes of text.
  2. Compare the complete polynomial and width; some notations omit the leading coefficient 1.
  3. Match the remaining parameters and use a published check example for that profile before comparing outputs.
1101 can describe different inputs

In this lesson 1101 contains four bits. As text in a file-oriented calculator the same writing may become four character bytes. Here 1011 is the complete coefficient string for x³ + x + 1; it is not the name of an industrial profile.

The lesson tool implements only the declared direct division. It checks the steps of these exercises. To interoperate with a real protocol, read its specification and use its profile and check examples; do not infer parameters from an output that seems convenient.

Transfer the method: generator 111 and nine data bits

For G = 111, representing x² + x + 1, r = 2. Data 111101100 contain nine bits and represent 1EC₁₆. Append 00 and divide 11110110000. Successive XOR steps leave 00010110000, 00001010000, 00000100000, 00000011000, 00000000100 and 00000000011.

The remainder is 11; the transmitted codeword is 11110110011, containing 11 bits, or 7B3₁₆. Dividing it by 111 gives 00. Omitting the final data zero would describe a different message and produce a different result. This is an example from the previous materials, rather than an unseen problem reserved for assessment.

A mistake to avoid: Do not compare results before establishing that inputs and conventions match.

The same rule applies to a software library: documentation and check examples are part of verification.

Supplement · A visual code is not our Hamming example

The visual representation of data and its correction method are distinct. QR uses Reed–Solomon error correction; we do not directly apply this lesson’s three Hamming checks to a QR image.

Why this method works

Visual examples are familiar but a shared purpose does not imply the same algorithm. Recognising the application should not turn an introduction into a false technical promise.

Steps to follow

  1. Separate reading the image, decoding the information and handling errors.
  2. For a specific format read its documentation: structure, correction level and conditions.
  3. If you scan a damaged example, report the outcome as an observation about that case rather than a guarantee for all damage.
What can a phone-scanning experiment establish?

If a phone reads a partially covered QR code, we observe that this example, device and damage pattern were decoded. A single scan does not establish a universal fraction of the image that can be missing. Damage position and structure can matter, and percentages in documentation must not be reinterpreted without context.

The shared idea is redundancy supporting recovery under defined conditions. The concrete algorithm differs. No QR generator installation, camera use or image submission is needed to complete this seminar.

QR restoration percentages in documentation concern codewords, rather than a guaranteed percentage of raw bits or image area. Multiplying them by a raw bit length does not automatically establish the number of correctable errors.

A mistake to avoid: Do not call every code with check bits “Hamming” or turn an observation into a general guarantee.

When investigating with Gemini, first verify the exact format name and the source describing its method.

Tools for checking calculations

Calculate first and state the convention. The tools apply the declared rules and show what the checks allow us to infer. A passing check does not prove the absence of every error. Answers are not sent to a server and receive no gradebook points.

Even parity: one bit appended on the right

Encoding takes 1–64 data bits and appends one bit on the right. Verification takes the complete word of 2–65 bits. An odd number of changed bits is detected; an even number may go undetected. This check neither locates nor corrects the error.

Hamming: encoding, syndrome and correction under an explicit assumption

Number positions from the left: 1, 2, 3… Even parity bits occupy positions 1, 2 and 4; for (12,8), also position 8. Data occupy the remaining positions in written order. SECDED (8,4) appends the parity of the whole seven-bit Hamming word on the right, at position 8. Changing a bit in the tool is your chosen experiment; the decoder does not learn how many bits you changed.

Exactly four data bits and seven bits in the received word. Interpreting a correction assumes at most one bit error.

Teaching CRC: binary division from left to right

Enter 1–64 data bits and a 2–17-bit generator, starting and ending with 1. The degree r is the generator length minus 1. Append r zeroes, divide using XOR and retain an exactly r-bit remainder. Verification takes the complete word: more than r bits, at most 80. The initial register is zero, with no reflection or final XOR. This is a teaching example, not an implicit implementation of a commercial CRC.

Show the XOR steps of the latest division

Each row has the dividend’s length. The generator is aligned with the leading 1 used in the step; outer zeroes show the alignment. XOR uses no borrowing or carry. A quotient bit of 0 needs no XOR step.

Encode or check to display the steps.
