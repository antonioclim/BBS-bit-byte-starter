Ce investighezi și de ce

Aplicația interpretează aceiași opt biți fără semn și cu semn. Funcția cu semn conține o greșeală didactică. Astăzi o reproduci, scrii ce crezi că o provoacă, analizezi o explicație Gemini și alegi un test care poate deosebi explicațiile.

Git păstrează legătura dintre problemă și remediere: un issue descrie problema, o ramură separă lucrul la remediere, iar un pull request explică schimbarea înainte de integrarea în main. Vei face aceste operații în propriul repository.

Plan orientativ, încă neverificat cu grupele. Activitățile de mai jos includ quizul și încap în cele 90 de minute; indiciile se folosesc în etapa curentă.

Sursa comună este BBS-bit-byte-starter, dar origin trebuie să indice repository-ul tău. pull preia din copia ta online; nu aduce automat actualizările ulterioare ale template-ului. 2 · Prezice interpretarea cu semn și reproduce problema

În PROJECT/evidence.md, completează întâi așteptările pentru 127, 128 și 129. În complement față de doi pe opt biți, intervalul este −128…127. Regula este:

s = u pentru u < 128; s = u − 256 pentru u ≥ 128.

2 · Prezice interpretarea cu semn și reproduce problema
Fără semn uBinarCu semn s, așteptatCalcul
12701111111127Pragul nu este atins.
12810000000−128128 − 256 = −128.
12910000001−127129 − 256 = −127.
25511111111−1255 − 256 = −1.

Deschide aplicația locală și introdu 127, 128 și 129. Notează binarul și interpretarea cu semn obținută. În proiectul de pornire, 128 apare greșit ca 128, deși binarul este 10000000. Vecinii 127 și 129 sunt interpretați corect.

Aceiași biți pot avea două interpretări; nu îi modifici ca să treci de la fără semn la cu semn. Investigația trebuie să explice de ce greșeala apare chiar la prag, fără să presupună că toate conversiile sunt greșite.

De unde vine pragul 128?

Fără semn, pozițiile au ponderile 128, 64, 32, 16, 8, 4, 2 și 1. În complement față de doi, prima pondere este −128, iar celelalte rămân pozitive. Astfel, 10000000 înseamnă −128, iar 10000001 înseamnă −128 + 1 = −127.

Pentru un șir care începe cu 1, diferența dintre cele două interpretări este 256: ponderea +128 devine −128. De aici vine regula u − 256. Nu este o scădere aleasă arbitrar.

3 · Scrie ipoteza ta înainte de Gemini și deschide un issue

În PROJECT/evidence.md, scrie două propoziții: „Cred că problema apare deoarece…” și „Dacă această explicație este corectă, testul… ar trebui să arate…”. Nu trebuie să ghicești de la început cauza corectă. Ipoteza trebuie să poată fi comparată cu o observație.

De exemplu, „la 128 se pierde primul bit” prezice alt binar; „condiția nu include exact pragul” prezice binar corect, dar interpretare greșită numai la 128. Aceste explicații se pot deosebi prin verificarea separată a celor două rezultate.

Pe GitHub, în repository-ul tău, alege Issues → New issue. Scrie un titlu precum „Interpretarea cu semn pentru 128” și completează:

Unde se copiază: în descrierea issue-ului din repository-ul tău GitHub.

Intrare și pași de reproducere: ...
Rezultat așteptat: ...
Rezultat obținut: ...
Ipoteza mea înainte de Gemini: ...
Test care poate deosebi explicațiile: ...
Criteriu de încheiere: pragul este corect, iar cazurile deja corecte rămân corecte.

Păstrează numărul issue-ului. El va lega descrierea problemei de pull request-ul remedierii. Dacă fila Issues lipsește, verifică repository-ul și semnalează setarea; până se rezolvă, păstrează rubricile în evidence.md.

4 · Analizează o explicație Gemini, apoi verifică o afirmație

Acum deschide Gemini în browser și folosește promptul după ce înlocuiești rubrica ipotezei. Dacă nu ai acces sau ai atins limita disponibilă, folosește exemplul didactic pregătit. Activitatea este aceeași și nu cere un abonament plătit.

Unde se copiază: în Gemini, după completarea rubricilor tale.

Investighez o funcție care interpretează un octet în complement față de doi. Pentru 127, 128 și 129 obțin 127, 128 și −127. Din definiție aștept 127, −128 și −127. Ipoteza mea inițială este: [scriu ipoteza]. Nu îmi da încă funcția corectată. Propune două explicații posibile și câte un test care le-ar putea deosebi. Explică de ce 128 este important. Separă ce rezultă din definiție de ce trebuie verificat în program.
  1. Alege o afirmație precisă din răspuns, nu verdictul „pare corect”.
  2. Stabilește ce rezultat ar susține-o și ce rezultat ar contrazice-o.
  3. Rulează testul în aplicație, fără să fi reparat încă funcția.
  4. Notează intrarea, așteptarea, rezultatul și concluzia în evidence.md.

Exemplu: afirmația „dacă binarul este corect, problema nu este pierderea primului bit în afișare” poate fi cercetată la 128. Observi 10000000, dar s = 128: ai un motiv să inspectezi interpretarea cu semn. Această observație nu dovedește încă faptul că orice altă linie a programului este corectă.

Dacă răspunsul oferă direct cod, cere explicația și testul înainte să îl folosești. Păstrează numai afirmația aleasă, nu întreaga conversație. O ipoteză inițială greșită nu este penalizată; arată ce observație te-a făcut să o revizuiești.

Prompt opțional pentru un contraexemplu

Folosește-l când explicația generalizează din câteva rezultate:

Unde se copiază: în Gemini, după completarea rubricilor tale.

Afirmația pe care o verific este: [afirmația precisă]. Exemplele mele sunt: [intrări și rezultate]. Propune un contraexemplu în 0–255 sau explică de ce exemplele nu sunt suficiente. Pentru testul propus, precizează rezultatul așteptat din definiție. Nu presupune că ai rulat proiectul meu.

Lasă o urmă scurtă a raționamentului

Completează rubricile S06 din evidence.md. Modelul de mai jos te ajută să legi afirmația de un rezultat observabil. Scrie predicția înainte să rulezi. Dacă binarul și valoarea cu semn nu se potrivesc, urmărește-le separat; un rezultat final greșit nu spune singur care operație l-a produs.

Unde se copiază: în secțiunea S06 din PROJECT/evidence.md.

Afirmația aleasă și sursa: ...
Testul meu: intrarea ...; verific binarul / interpretarea cu semn / ambele.
Înainte de rulare, aștept ... deoarece ...
Explicația ar fi contrazisă dacă observ ...
După rulare, am observat ...
Concluzia: ...; acest test nu dovedește că ...

O singură afirmație verificată este suficientă pentru activitate. Nu ai nevoie de un chat lung, de capturi sau de un document suplimentar. Ipoteza inițială poate fi greșită; important este să explici ce observație te-a făcut să o păstrezi sau să o schimbi.

5 · Creează ramura și adaugă testul care expune greșeala

Revino în VS Code. Notele investigației pot fi încă neînregistrate. Citește git status și diff-ul: dacă sunt numai notele și testele de azi, creezi din main o ramură nouă și continui acolo. Nu executa între timp pull peste modificări neînregistrate.

Apasă numele ramurii din bara de stare → Create new branch, cu numele fix/signed-boundary. Sau folosește comanda de mai jos o singură dată:

Unde se copiază: în terminalul VS Code, din rădăcina repository-ului.

git switch -c fix/signed-boundary
git branch --show-current

Ultima comandă și bara de stare trebuie să arate fix/signed-boundary. Ramura pornește din aceeași versiune ca main, dar îți permite să explici remedierea înainte de integrare.

Testul propriu pentru 128 este obligatoriu în S06. În PROJECT/custom-tests.js, păstrează obiectele existente, pune virgulă după ultimul și adaugă înainte de ];:

Unde se copiază: în lista CustomTests din PROJECT/custom-tests.js.

{ label: 'Pragul interpretării cu semn', input: 128, operation: 'signed', expected: -128 }

expected este număr, fără ghilimele. Salvează și reîncarcă PROJECT/tests.html. Selectează S06 și rulează din nou; testele proprii sunt incluse automat: înainte de remediere, testul pentru 128 trebuie să eșueze. Ai făcut greșeala reproductibilă, nu ai stricat programul adăugând testul.

De ce nu ne ajung 0 și 255?

Ambele sunt corecte în funcția de pornire. Condiția greșită diferă de cea corectă numai la 128, deci exemplele obișnuite o pot rata. Alege 127, 128 și 129 pentru a compara valoarea imediat de sub prag, pragul și valoarea imediat de peste el. 255 verifică și extrema intervalului.

De ce văd mai multe teste eșuate pentru aceeași greșeală?

Cu hexazecimalul S05 completat, etapa S06 detectează greșeala în două verificări furnizate: cazul individual 128 și verificarea tuturor celor 256 de valori cu semn. După adăugarea testului tău pentru 128, apare și al treilea eșec. Este aceeași intrare greșită observată prin trei verificări.

Testele proprii se execută în orice etapă selectată. De aceea, după adăugarea testului cu semn, și S05 îl va raporta ca eșuat până la remediere. Verificarea S05 de la început s-a făcut înaintea adăugării lui. Nu șterge testul ca să obții verde; după corectare trebuie să treacă și acesta. Alte teste adăugate de tine pot schimba numărul rezultatelor.

6 · Repară condiția și verifică din nou

În PROJECT/lab.js, găsește asSigned8. Linia return u > 128 ? u - 256 : u; întreabă dacă u este strict mai mare decât 128. Pentru u = 128 condiția este falsă, iar funcția întoarce u nemodificat.

Compară cu regula matematică: scăderea lui 256 trebuie aplicată și la u = 128. Modifică numai condiția necesară, păstrând validarea și celelalte funcții.

Indiciu de sintaxă, după ce ai investigat

condiție ? A : B alege A când condiția este adevărată și B când este falsă. Operatorul >= include egalitatea, pe când > o exclude. Verifică ce ramură se alege pentru 128 după schimbare.

  1. Salvează și reîncarcă aplicația. Verifică 127 → 127, 128 → −128, 129 → −127 și 255 → −1.
  2. Reîncarcă pagina de teste, selectează S06 și rulează. Testul propriu pentru 128 trebuie acum să treacă.
  3. Citește și verificările S05 incluse: schimbarea nu trebuie să strice hexazecimalul sau validarea.
  4. În README actualizează ce este implementat. În evidence.md păstrează ipoteza inițială, sursa, afirmația, testul și concluzia.

Pregătește fișa de reluare înainte de commit: „După integrare verific main, pull și testele S06; la S07 încep paritatea”. Astfel publici notele împreună cu remedierea, fără un raport separat.

Ce înseamnă un test de regresie?

Este verificarea unui comportament care era deja corect, după o schimbare. Repararea lui 128 nu îți dă dreptul să presupui că 127, 129, 255 sau hexazecimalul au rămas corecte. Le rulezi din nou. Testele compară rezultate cu referința; nu certifică autorul codului.

7 · Publică ramura și explică integrarea în propriul PR

În Source Control citește diferențele și selectează fișierele relevante cu +. Fă commit cu un mesaj precum S06: corectarea pragului interpretarii cu semn, apoi Publish Branch. Dacă ramura are deja o legătură online, folosește Push.

Alternativă în terminal

Din rădăcina repository-ului:

Unde se copiază: în terminalul VS Code, din rădăcina repository-ului.

Pe GitHub, în repository-ul tău, alege Pull requests → New pull request sau Compare & pull request. Verifică base: main și compare: fix/signed-boundary, ambele în copia ta. Completează câteva rânduri; înlocuiește #NUMAR cu issue-ul real:

Unde se copiază: în descrierea pull request-ului din repository-ul tău GitHub.

Problema: interpretarea cu semn pentru 128. Issue: #NUMAR
Modificarea: ...

În Files changed citește schimbarea încă o dată. După verificare, alege metoda Create a merge commit din meniul de lângă buton, dacă nu este deja selectată. Apasă Merge pull request, apoi Confirm merge. Închide issue-ul cu rezultatul. Nu aștepta ca fiecare PR să fie aprobat individual de cadrul didactic: în această activitate exersezi explicarea și integrarea propriei schimbări.

Acest PR propriu nu este o verificare făcută de un coleg. Testele rulează local; lipsa unui rezultat GitHub Actions pe PR nu spune dacă ai executat testele.

8 · După merge, actualizează copia locală și rezolvă Q06

Merge-ul de pe GitHub integrează schimbarea online, dar nu modifică singur copia din VS Code. Verifică să nu mai ai modificări neînregistrate, apoi rulează din rădăcină:

Unde se copiază: în terminalul VS Code, din rădăcina repository-ului.

git status
git switch main
git pull --ff-only
git status
git log -3 --oneline

Acum trebuie să fii pe main, cu stare curată și integrarea vizibilă în istoric. Rerulează testele S06 din această copie. Dacă pull refuză sau merge-ul a fost blocat, păstrează mesajul și verifică dacă PR-ul a fost integrat, nu doar închis. Nu folosi reset --hard sau force push pentru a ascunde problema.

În minutele 75–85 rezolvă Q06 în Moodle, individual, fără AI sau colegi. Fișa comună de referință este permisă. Maximum 30 de puncte interne înseamnă 0,30 puncte reale. Vei explica pragul, alegerea testelor, limitele unei afirmații și relația dintre branch, merge și pull.

Metoda rămâne utilă la orice regulă cu praguri: calcule fiscale, limite de vârstă, intervale sau validări. O explicație convingătoare trebuie să reziste unui test ales cu grijă. La S07 adaugi o cerință și verifici versiunea finală →
