S06 · Investighezi şi repari

Scrii o ipoteză, verifici o afirmaţie şi păstrezi o remediere explicată.

Ce investighezi şi de ce

Aplicaţia interpretează aceiaşi opt biţi fără semn şi cu semn. Funcţia cu semn conţine o greşeală didactică. Astăzi o reproduci, scrii ce crezi că o provoacă, analizezi o explicaţie Gemini şi alegi un test care poate deosebi explicaţiile.

Git păstrează legătura dintre problemă şi remediere: un issue descrie problema, o ramură separă lucrul la remediere, iar un pull request explică schimbarea înainte de integrarea în main. Vei face aceste operaţii în propriul repository.

Sursa comună este BBS-bit-byte-starter, dar origin trebuie să indice repository-ul tău. pull preia din copia ta online; nu aduce automat actualizările ulterioare ale template-ului. 2 · Prezice interpretarea cu semn şi reproduce problema

În PROJECT/evidence.md, completează întâi aşteptările pentru 127, 128 şi 129. În complement faţă de doi pe opt biţi, intervalul este −128…127. Regula este:

s = u pentru u < 128; s = u − 256 pentru u ≥ 128.

2 · Prezice interpretarea cu semn şi reproduce problema
Fără semn uBinarCu semn s, aşteptatCalcul
12701111111127Pragul nu este atins.
12810000000−128128 − 256 = −128.
12910000001−127129 − 256 = −127.
25511111111−1255 − 256 = −1.

Deschide aplicaţia locală şi introdu 127, 128 şi 129. Notează binarul şi interpretarea cu semn obţinută. În proiectul de pornire, 128 apare greşit ca 128, deşi binarul este 10000000. Vecinii 127 şi 129 sunt interpretaţi corect.

Aceiaşi biţi pot avea două interpretări; nu îi modifici ca să treci de la fără semn la cu semn. Investigaţia trebuie să explice de ce greşeala apare chiar la prag, fără să presupună că toate conversiile sunt greşite.

De unde vine pragul 128?

Fără semn, poziţiile au ponderile 128, 64, 32, 16, 8, 4, 2 şi 1. În complement faţă de doi, prima pondere este −128, iar celelalte rămân pozitive. Astfel, 10000000 înseamnă −128, iar 10000001 înseamnă −128 + 1 = −127.

Pentru un şir care începe cu 1, diferenţa dintre cele două interpretări este 256: ponderea +128 devine −128. De aici vine regula u − 256. Nu este o scădere aleasă arbitrar.

3 · Scrie ipoteza ta înainte de Gemini şi deschide un issue

În PROJECT/evidence.md, scrie două propoziţii: „Cred că problema apare deoarece…” şi „Dacă această explicaţie este corectă, testul… ar trebui să arate…”. Nu trebuie să ghiceşti de la început cauza corectă. Ipoteza trebuie să poată fi comparată cu o observaţie.

De exemplu, „la 128 se pierde primul bit” prezice alt binar; „condiţia nu include exact pragul” prezice binar corect, dar interpretare greşită numai la 128. Aceste explicaţii se pot deosebi prin verificarea separată a celor două rezultate.

Pe GitHub, în repository-ul tău, alege Issues → New issue. Scrie un titlu precum „Interpretarea cu semn pentru 128” şi completează:

Unde se copiază: în descrierea issue-ului din repository-ul tău GitHub.

Intrare şi paşi de reproducere: ...
Rezultat aşteptat: ...
Rezultat obţinut: ...
Ipoteza mea înainte de Gemini: ...
Test care poate deosebi explicaţiile: ...
Criteriu de încheiere: pragul este corect, iar cazurile deja corecte rămân corecte.

Păstrează numărul issue-ului. El va lega descrierea problemei de pull request-ul remedierii. Dacă fila Issues lipseşte, verifică repository-ul şi semnalează setarea; până se rezolvă, păstrează rubricile în evidence.md.

4 · Analizează o explicaţie Gemini, apoi verifică o afirmaţie

Acum deschide Gemini în browser şi foloseşte promptul după ce înlocuieşti rubrica ipotezei. Dacă nu ai acces sau ai atins limita disponibilă, foloseşte exemplul didactic pregătit. Activitatea este aceeaşi şi nu cere un abonament plătit.

Unde se copiază: în Gemini, după completarea rubricilor tale.

Investighez o funcţie care interpretează un octet în complement faţă de doi. Pentru 127, 128 şi 129 obţin 127, 128 şi −127. Din definiţie aştept 127, −128 şi −127. Ipoteza mea iniţială este: [scriu ipoteza]. Nu îmi da încă funcţia corectată. Propune două explicaţii posibile şi câte un test care le-ar putea deosebi. Explică de ce 128 este important. Separă ce rezultă din definiţie de ce trebuie verificat în program.
  1. Alege o afirmaţie precisă din răspuns, nu verdictul „pare corect”.
  2. Stabileşte ce rezultat ar susţine-o şi ce rezultat ar contrazice-o.
  3. Rulează testul în aplicaţie, fără să fi reparat încă funcţia.
  4. Notează intrarea, aşteptarea, rezultatul şi concluzia în evidence.md.

Exemplu: afirmaţia „dacă binarul este corect, problema nu este pierderea primului bit în afişare” poate fi cercetată la 128. Observi 10000000, dar s = 128: ai un motiv să inspectezi interpretarea cu semn. Această observaţie nu dovedeşte încă faptul că orice altă linie a programului este corectă.

Dacă răspunsul oferă direct cod, cere explicaţia şi testul înainte să îl foloseşti. Păstrează numai afirmaţia aleasă, nu întreaga conversaţie. O ipoteză iniţială greşită nu este penalizată; arată ce observaţie te-a făcut să o revizuieşti.

Prompt opţional pentru un contraexemplu

Foloseşte-l când explicaţia generalizează din câteva rezultate:

Unde se copiază: în Gemini, după completarea rubricilor tale.

Afirmaţia pe care o verific este: [afirmaţia precisă]. Exemplele mele sunt: [intrări şi rezultate]. Propune un contraexemplu în 0–255 sau explică de ce exemplele nu sunt suficiente. Pentru testul propus, precizează rezultatul aşteptat din definiţie. Nu presupune că ai rulat proiectul meu.

Lasă o urmă scurtă a raţionamentului

Completează rubricile S06 din evidence.md. Modelul de mai jos te ajută să legi afirmaţia de un rezultat observabil. Scrie predicţia înainte să rulezi. Dacă binarul şi valoarea cu semn nu se potrivesc, urmăreşte-le separat; un rezultat final greşit nu spune singur care operaţie l-a produs.

Unde se copiază: în secţiunea S06 din PROJECT/evidence.md.

Afirmaţia aleasă şi sursa: ...
Testul meu: intrarea ...; verific binarul / interpretarea cu semn / ambele.
Înainte de rulare, aştept ... deoarece ...
Explicaţia ar fi contrazisă dacă observ ...
După rulare, am observat ...
Concluzia: ...; acest test nu dovedeşte că ...

O singură afirmaţie verificată este suficientă pentru activitate. Nu ai nevoie de un chat lung, de capturi sau de un document suplimentar. Ipoteza iniţială poate fi greşită; important este să explici ce observaţie te-a făcut să o păstrezi sau să o schimbi.

5 · Creează ramura şi adaugă testul care expune greşeala

Revino în VS Code. Notele investigaţiei pot fi încă neînregistrate. Citeşte git status şi diff-ul: dacă sunt numai notele şi testele de azi, creezi din main o ramură nouă şi continui acolo. Nu executa între timp pull peste modificări neînregistrate.

Apasă numele ramurii din bara de stare → Create new branch, cu numele fix/signed-boundary. Sau foloseşte comanda de mai jos o singură dată:

Unde se copiază: în terminalul VS Code, din rădăcina repository-ului.

git switch -c fix/signed-boundary
git branch --show-current

Ultima comandă şi bara de stare trebuie să arate fix/signed-boundary. Ramura porneşte din aceeaşi versiune ca main, dar îţi permite să explici remedierea înainte de integrare.

Testul propriu pentru 128 este obligatoriu în S06. În PROJECT/custom-tests.js, păstrează obiectele existente, pune virgulă după ultimul şi adaugă înainte de ];:

Unde se copiază: în lista CustomTests din PROJECT/custom-tests.js.

{ label: 'Pragul interpretării cu semn', input: 128, operation: 'signed', expected: -128 }

expected este număr, fără ghilimele. Salvează şi reîncarcă PROJECT/tests.html. Selectează S06 şi rulează din nou; testele proprii sunt incluse automat: înainte de remediere, testul pentru 128 trebuie să eşueze. Ai făcut greşeala reproductibilă, nu ai stricat programul adăugând testul.

De ce nu ne ajung 0 şi 255?

Ambele sunt corecte în funcţia de pornire. Condiţia greşită diferă de cea corectă numai la 128, deci exemplele obişnuite o pot rata. Alege 127, 128 şi 129 pentru a compara valoarea imediat de sub prag, pragul şi valoarea imediat de peste el. 255 verifică şi extrema intervalului.

De ce văd mai multe teste eşuate pentru aceeaşi greşeală?

Cu hexazecimalul S05 completat, etapa S06 detectează greşeala în două verificări furnizate: cazul individual 128 şi verificarea tuturor celor 256 de valori cu semn. După adăugarea testului tău pentru 128, apare şi al treilea eşec. Este aceeaşi intrare greşită observată prin trei verificări.

Testele proprii se execută în orice etapă selectată. De aceea, după adăugarea testului cu semn, şi S05 îl va raporta ca eşuat până la remediere. Verificarea S05 de la început s-a făcut înaintea adăugării lui. Nu şterge testul ca să obţii verde; după corectare trebuie să treacă şi acesta. Alte teste adăugate de tine pot schimba numărul rezultatelor.

6 · Repară condiţia şi verifică din nou

În PROJECT/lab.js, găseşte asSigned8. Linia return u > 128 ? u - 256 : u; întreabă dacă u este strict mai mare decât 128. Pentru u = 128 condiţia este falsă, iar funcţia întoarce u nemodificat.

Compară cu regula matematică: scăderea lui 256 trebuie aplicată şi la u = 128. Modifică numai condiţia necesară, păstrând validarea şi celelalte funcţii.

Indiciu de sintaxă, după ce ai investigat

condiţie ? A : B alege A când condiţia este adevărată şi B când este falsă. Operatorul >= include egalitatea, pe când > o exclude. Verifică ce ramură se alege pentru 128 după schimbare.

  1. Salvează şi reîncarcă aplicaţia. Verifică 127 → 127, 128 → −128, 129 → −127 şi 255 → −1.
  2. Reîncarcă pagina de teste, selectează S06 şi rulează. Testul propriu pentru 128 trebuie acum să treacă.
  3. Citeşte şi verificările S05 incluse: schimbarea nu trebuie să strice hexazecimalul sau validarea.
  4. În README actualizează ce este implementat. În evidence.md păstrează ipoteza iniţială, sursa, afirmaţia, testul şi concluzia.

Pregăteşte fişa de reluare înainte de commit: „După integrare verific main, pull şi testele S06; la S07 încep paritatea”. Astfel publici notele împreună cu remedierea, fără un raport separat.

Ce înseamnă un test de regresie?

Este verificarea unui comportament care era deja corect, după o schimbare. Repararea lui 128 nu îţi dă dreptul să presupui că 127, 129, 255 sau hexazecimalul au rămas corecte. Le rulezi din nou. Testele compară rezultate cu referinţa; nu certifică autorul codului.

Acest PR propriu nu este o verificare făcută de un coleg. Testele rulează local; lipsa unui rezultat GitHub Actions pe PR nu spune dacă ai executat testele.

8 · După merge, actualizează copia locală şi rezolvă Q06

Merge-ul de pe GitHub integrează schimbarea online, dar nu modifică singur copia din VS Code. Verifică să nu mai ai modificări neînregistrate, apoi rulează din rădăcină:

Unde se copiază: în terminalul VS Code, din rădăcina repository-ului.

git status
git switch main
git pull --ff-only
git status
git log -3 --oneline

Acum trebuie să fii pe main, cu stare curată şi integrarea vizibilă în istoric. Rerulează testele S06 din această copie. Dacă pull refuză sau merge-ul a fost blocat, păstrează mesajul şi verifică dacă PR-ul a fost integrat, nu doar închis. Nu folosi reset --hard sau force push pentru a ascunde problema.

În minutele 75–85 rezolvă Q06 în Moodle, individual, fără AI sau colegi. Fişa comună de referinţă este permisă. Maximum 30 de puncte interne înseamnă 0,30 puncte reale. Vei explica pragul, alegerea testelor, limitele unei afirmaţii şi relaţia dintre branch, merge şi pull.

Metoda rămâne utilă la orice regulă cu praguri: calcule fiscale, limite de vârstă, intervale sau validări. O explicaţie convingătoare trebuie să reziste unui test ales cu grijă. La S07 adaugi o cerinţă şi verifici versiunea finală →
