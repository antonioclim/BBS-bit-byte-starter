Ce finalizați astăzi

Implementați bitul de paritate pentru varianta atribuită. Testați, documentați și publicați modificările, apoi clonați proiectul într-un director separat pentru a verifica versiunea depusă.

La final, veți putea deosebi două verificări: paritatea cuvântului de biți și reproducerea rezultatelor din versiunea publicată. Fiecare susține o concluzie limitată la proprietatea verificată.

Planul este orientativ și nu a fost măsurat cu o grupă. Cele 90 de minute includ 70 de minute pentru proiect și depunere, 15 minute pentru Q07 și cinci minute pentru recapitulare. Consultați indiciile în etapa corespunzătoare.

2 · Înțelegeți cerința și preziceți bitul de control

Varianta atribuită în seminar este A — even, paritate pară sau B — odd, paritate impară. Implementați numai modul atribuit. În README precizați varianta completată și modul care rămâne intenționat neimplementat.

Numărați biții 1 din cei opt biți de date: numim acest număr k. Adăugați un bit p la dreapta, astfel încât totalul k + p să fie par pentru A sau impar pentru B. Dacă totalul are deja paritatea cerută, adăugați 0; dacă trebuie schimbată, adăugați 1.

2 · Înțelegeți cerința și preziceți bitul de control
DatekA: p pentru total parB: p pentru total impar
3 = 0000001120: total 2.1: total 3.
7 = 0000011131: total 4.0: total 3.

În PROJECT/evidence.md, înainte de implementare, notați rezultatele așteptate pentru 3 și 7 în varianta atribuită. Precizați și că intrarea 256 trebuie respinsă, deoarece depășește intervalul unui octet fără semn.

Opt biți de date + un bit separat de paritate = un cuvânt de nouă biți. Octetul păstrează opt biți, iar interpretarea cu semn nu se modifică. Pentru A și 3, cuvântul transmis este 000000110; ultimul 0 este bitul de control.
Cum scrieți regula prin restul împărțirii?

În JavaScript, k % 2 este restul împărțirii la 2: 0 dacă k este par și 1 dacă k este impar. Pentru A, p = k % 2. Pentru B, p = 1 − (k % 2). Rezultatul trebuie să fie numărul 0 sau 1, nu text și nu valoarea totală k + p.

3 · Observați starea inițială și implementați varianta atribuită

Înainte să modificați funcția: păstrați predicțiile pentru 3 și 7 și adăugați cele trei teste proprii folosind blocul variantei dumneavoastră de la pasul 4. Păstrați testele existente, inclusiv testul pentru 128 din S06. Salvați și reîncărcați PROJECT/tests.html, selectați S07 și varianta atribuită și rulați testele.

Cu paritatea încă necompletată, cazurile 3 și 7 apar ca Neimplementat, fără a constitui rezultate corecte. Testul pentru 256 trebuie să treacă deja, deoarece validarea este furnizată. Consemnați starea inițială, apoi implementați regula. Nu modificați rezultatele așteptate pentru a le potrivi unei implementări greșite.

În PROJECT/lab.js identificați funcția parityBit8(u, mode). Validarea și două blocuri există deja: if (mode === 'even') și if (mode === 'odd'). Înlocuiți return null; numai în blocul variantei dumneavoastră.

Funcția auxiliară countOnes8(u) este furnizată și întoarce k. Puteți folosi const k = countOnes8(u);, urmată de instrucțiunea return cu regula dedusă. Verificați mai întâi pe hârtie rezultatul expresiei pentru k = 2 și k = 3.

Salvați și reîncărcați aplicația. Selectați modul implementat și comparați rezultatele cu predicțiile. Pentru celălalt mod, starea neimplementată este intenționată: sarcina privește numai varianta atribuită.

Indicii pentru încercarea proprie

Deschideți indiciile pe rând și opriți-vă când puteți continua.

1 · Regula totalului

Priviți totalul biților 1 după adăugarea bitului: trebuie să fie par pentru A sau impar pentru B. Ce se schimbă când adăugați 1?

Funcția countOnes8(u) numără biții 1. Paritatea valorii zecimale poate fi diferită de paritatea acestei numărători; regula folosește numărul de biți 1.

Citiți operația și starea fiecărui rând, fără a șterge testele. Folosiți numai setul variantei atribuite; celălalt mod rămâne intenționat neimplementat.

Dacă un test eșuează
  • Neimplementat: verificați varianta selectată și blocul editat.
  • Rezultatele sunt mereu inverse: verificați diferența dintre paritate pară și paritate impară.
  • Tip de rezultat greșit: funcția întoarce un număr 0 sau 1, nu textul '0' sau '1'.
  • Testele proprii nu apar: verificați virgulele dintre obiecte, salvarea și reîncărcarea paginii.
  • S05/S06 eșuează: inspectați diferențele pentru a identifica modificări accidentale în alte funcții.
Ce erori poate detecta paritatea?

Pentru A, datele 3 dau 000000110, cu doi biți 1. Dacă un 0 din date devine 1, totalul devine trei și verificarea semnalează eroarea. Dacă doi biți 0 devin 1, totalul devine patru și rămâne par; eroarea trece această verificare.

Inversarea unui bit, inclusiv a bitului de control, schimbă paritatea. Orice număr impar de inversări în poziții distincte este detectat; un număr par păstrează paritatea. Verificarea simplă nu localizează eroarea și nu o corectează.

5 · Pregătiți predarea, apoi faceți ultimul commit și push

În PROJECT/README.md, precizați varianta S07 implementată și modul de pornire: deschideți PROJECT/index.html și PROJECT/tests.html în browser și selectați S07 și varianta atribuită. În evidence.md pregătiți rezultatele, afirmația S06, verificarea și sursa. Folosiți fișa finală pentru rubrici.

Pregătiți textul fișei pe parcurs, astfel încât în minutele 68–70 să completați numai ultimele informații și să salvați depunerea. Confirmarea clonării se adaugă după verificare; nu declarați efectuarea unei operații care nu a avut loc.

Identificatorul final SHA se copiază în Moodle după ultimul commit și push. Nu îl introduceți în evidence.md pentru a înregistra apoi fișierul într-un commit: această operație ar crea un commit nou, cu alt identificator.

În Source Control inspectați diferențele, selectați fișierele relevante, înregistrați commitul și folosiți Push pe main. Verificați în GitHub ultimul mesaj și funcția. Puteți folosi, din rădăcina proiectului:

Unde se copiază: în terminalul VS Code, din rădăcina depozitului de cod.

git status
git diff
git add PROJECT/lab.js PROJECT/custom-tests.js PROJECT/README.md PROJECT/evidence.md
git diff --cached

Ultima comandă afișează identificatorul complet al commitului local. Folosiți-l pentru depunere după confirmarea unui push reușit. Dacă modificați ulterior proiectul, publicați noua versiune, preluați noul SHA și repetați verificarea.

6 · Verificați versiunea publicată dintr-o clonare nouă

Copia de lucru poate conține fișiere neincluse în commit. Clonarea separată permite verificarea conținutului disponibil efectiv pe GitHub.

  1. Copiați URL-ul HTTPS al proiectului propriu.
  2. În VS Code selectați Git: Clone, apoi alt director părinte, de exemplu Documents/BTI_REPRO. Clonați în afara proiectului inițial și fără a suprascrie o copie existentă.
  3. Deschideți noul director într-o fereastră separată și verificați calea completă, chiar dacă numele proiectului este același.
  4. În terminalul copiei noi executați verificările:

Unde se copiază: în terminalul VS Code, din rădăcina depozitului de cod.

git remote -v
git branch --show-current
git status
git rev-parse HEAD

Trebuie să vedeți depozitul de cod propriu, main, stare curată și același SHA complet ca după publicarea finală. Deschideți acum aplicația și testele din PROJECT al copiei noi. Verificați calea în bara de adrese; o filă deschisă anterior poate indica încă proiectul inițial.

Selectați S07 și varianta atribuită, rulați testele și confirmați cazurile pentru 3, 7 și 256. Depuneți rezultatele acestei rulări. Procedura verifică reproducerea versiunii publicate; nu identifică autorul fiecărei linii de cod.

Alternativă în terminal, cu un nume local diferit

Rulați dintr-un director părinte aflat în afara proiectului original. Înlocuiți contul și depozitul de cod. Directorul BTI_REPRO trebuie să nu existe deja:

Unde se copiază: în terminalul VS Code, din directorul părinte ales pentru clonare.

git clone https://github.com/CONTUL_TAU/REPOSITORY_UL_TAU.git BTI_REPRO
cd BTI_REPRO
git branch --show-current
git status
git rev-parse HEAD
Dacă SHA-ul diferă sau rezultatul nu se reproduce

Dacă identificatorii diferă, verificați URL-ul, ramura și ultimul push. Dacă lipsește un fișier, adăugați-l în copia inițială, testați și publicați un nou commit. Actualizați copia separată și verificați din nou SHA-ul și testele. Rezultatele dintr-o filă veche nu confirmă comportamentul noii clone.

Consemnați verificarea în Moodle, fără un commit suplimentar numai pentru această confirmare în evidence.md. Dacă un test continuă să eșueze, descrieți rezultatul observat; fișa trebuie să redea starea reală.
