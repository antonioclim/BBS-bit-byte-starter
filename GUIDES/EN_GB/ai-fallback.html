AI investigation and fallback

Make a prediction before reading an explanation, then use evidence to decide what to keep.

One claim, one test, one conclusion

Gemini can suggest an explanation, but it does not see every relevant part of your project unless you provide it. A confident answer is still a claim to check. Use your own definition-based prediction as the expected result, then compare what the program actually does.

  1. Record your own hypothesis before consulting the response.
  2. Select one precise claim. “This answer seems good” is too vague to test.
  3. Choose an input whose expected result would distinguish the claim from another explanation.
  4. Run that test and record expected and actual results separately.
  5. State what is supported, contradicted or still uncertain and why.

In S06, use Gemini if available or one prepared response below if not. The investigation is required; a paid service is not. A wrong initial hypothesis is acceptable when you preserve it and explain the evidence that changed your view.

If Gemini is unavailable

The responses below are prepared teaching responses, not transcripts of a live Gemini conversation. Record prepared fallback as the source. Select one response and carry out the same test-and-conclusion sequence.

Prepared response 1 · Separate the bits from the interpretation

The eight-bit pattern and its signed interpretation are different results. Compare 127, 128 and 129, checking both the displayed strings and signed values. If a string is correct but its signed value is wrong, investigate the signed rule’s choice of cases. These observations suggest where to look; they do not establish a repair until the implementation is checked and tests are rerun.

A testable claim: the binary string can be correct while the signed interpretation is wrong. Predict both results for 128, run the starter and compare them separately. Would changing the displayed string be justified by that evidence?

Prepared response 2 · Challenge a generalisation

The conversion gives the correct signed results for 0 and 255, so it appears correct throughout the byte range. If another value looks wrong, the displayed binary string may be causing the problem.

A testable claim: success at 0 and 255 is enough to trust the signed conversion throughout 0–255. Choose an input at the transition between nonnegative and negative signed values. Predict its string and signed value, then run it before changing the code.

Check your conclusion after running the test

The starter displays 10000000 for 128, which is the correct eight-bit string, but the signed rule should yield −128. Passing endpoints does not establish correctness for all intermediate inputs. After repairing the interpretation, rerun 127, 128, 129 and 255 so the failing case and its neighbours are checked.

Prompts you can adapt during practical work

Replace bracketed text with your own observations. Include only what is relevant: no credentials or unnecessary personal information. These prompts are not permitted during the quizzes.

S05 · Where does my work exist?

Paste into: Gemini prompt box · optional S05 clarification

I saved a file and created a commit in VS Code, but I have not pushed. Explain where the changed file and new commit now exist. Distinguish the working folder, local Git history and GitHub. Suggest two checks I can perform myself to see whether the new commit is published. Do not assume I ran commands I have not mentioned.

S06 · Investigate before receiving a fix

Paste into: Gemini prompt box · after recording your hypothesis

I am investigating a function that interprets an unsigned byte as eight-bit two’s complement. My own hypothesis is: [my hypothesis]. For 127, 128, 129 and 255, I expect: [values], and observe: [results]. Do not give replacement code immediately. Ask two diagnostic questions and suggest a test that could disprove my hypothesis. Keep the eight-bit pattern separate from its signed interpretation. Say which claims follow from the definition and which require checking the implementation.

S06 · Search for a counterexample

Paste into: Gemini prompt box · optional follow-up in S06

The precise claim I want to check is: [one claim]. The examples I have tested are: [inputs and results]. Is there a counterexample in 0–255, or are these examples insufficient to justify the claim? Suggest a distinguishing test and its expected result. Separate the mathematical definition from assumptions about the implementation.

S07 · Explain the parity requirement

Paste into: Gemini prompt box · optional S07 clarification

I need to append an [even/odd] parity bit to a data byte. For 00000011 and 00000111, explain which bit should be appended and why. Do not write the code. Give an example where a single-bit change is detected and one where two bit changes preserve parity. Keep the eight data bits separate from the additional check bit.
