S05 · Take over, check and publish

Create your own connected copy, make a small hexadecimal change and leave a published version you can resume.

Today’s question and result

How do I take over a project, make one change and know where that change exists? We will create your own repository from the course template, clone it, run its supplied behaviour and complete one function. You will finish with a tested hexadecimal output and a commit published to your own GitHub repository.

The requirement is precise: toHex8(u) receives a validated integer from 0 to 255 and returns two uppercase hexadecimal characters. Decimal 5 must become 05; decimal 255 must become FF.

The starter deliberately contains later work: signed interpretation has a known teaching defect and parity is unfinished. Run baseline before your change, then S05 afterwards. Later-stage failures do not mean you must complete S06 and S07 today.

1. Create your own GitHub repository, then clone it

Where: first Moodle and GitHub in the browser, then VS Code. The template is our starting project; your repository is where you can publish your work. Cloning creates its connected local copy.

  1. Open our shared BBS-bit-byte-starter template. Check the project name and your signed-in account.
  2. Select Use this template → Create a new repository. Set the owner to your own account and use a short name such as bti-byte-lab, following any naming rule announced for your group.
  3. Follow the course’s public/private visibility instruction. Copy only the default branch, not all template branches.
  4. Create the repository. Its URL must now contain your account and your chosen name. Check that it contains PROJECT, GUIDES and START.html.
  5. In your own repository’s Code → HTTPS menu, copy the URL.
  6. Open VS Code’s Command Palette with Ctrl+Shift+P on Windows/Linux or ⌘+Shift+P on macOS. Select Git: Clone and paste that URL.
  7. Select the prepared parent folder, for example Documents/BTI. Git creates the repository folder inside it. When cloning finishes, open that new folder. Authenticate as yourself if asked.

Check: VS Code’s Explorer shows your project files. In Terminal → New Terminal, run:

Paste into: VS Code terminal · repository root

git status
git remote -v

The working tree should be clean. The remote called origin must point to your own repository. Why: otherwise you could edit files successfully yet have no connection to the repository you intend to submit.

Before your first commit, check or set your repository-specific author name and email using Before S05. This does not replace GitHub authentication.

No template button, wrong owner or “not a git repository”

If Use this template is missing, check the course link and tell us; the teaching repository must be configured as a template. Do not substitute a fork or ZIP download. If the URL still names the teaching account, you are looking at the template: create and clone your own repository. If Git says “not a git repository”, use File → Open Folder to open the clone itself rather than its parent folder.

If authentication shows somebody else’s account, stop before pushing and follow the laboratory session arrangement. A local author setting cannot clear stored credentials.

Terminal alternative to Git: Clone

Use this only instead of the VS Code Clone command. Open a terminal in the prepared parent folder, replace the URL and run:

Paste into: VS Code terminal · prepared parent folder, before opening the clone

git clone "PASTE_YOUR_OWN_REPOSITORY_HTTPS_URL_HERE"

Then open the new repository folder. Do not run git init after cloning.

2. Predict, then run the supplied behaviour

Where: PROJECT/evidence.md in VS Code and PROJECT/index.html in a browser. Write your predictions for 0, 5 and 255 before entering them in the application. Record expected and observed binary strings separately.

  1. In VS Code, expand PROJECT. Reveal index.html in File Explorer/Finder, then open it with a browser.
  2. Select English in the application. Enter each predicted value; the interface updates automatically when input changes.
  3. Compare the eight-bit strings. A blank or unfinished hexadecimal field is expected at this stage.
  4. Open PROJECT/tests.html in the browser, select baseline and click Run.

Check: the supplied baseline checks pass. Why: you first establish what already works, so your later change can be checked against the same starting point. A passing baseline does not claim that unfinished functions work.

Prediction support after your first attempt

The bit weights are 128, 64, 32, 16, 8, 4, 2, 1. Decimal 5 is 4 + 1, so its pattern is 00000101. Zero is 00000000; 255 is the sum of all eight weights, so it is 11111111. Leading zeros preserve the eight-bit width.

The browser seems to ignore saved changes

Save in VS Code, then reload the browser page. Changing application input recalculates the result; it does not reload an edited JavaScript file. Check the browser’s local file path if more than one project folder is open.

3. Understand and complete the hexadecimal output

Why two characters? One hexadecimal digit has 16 possible values, exactly the combinations of four bits: 16 = 2⁴. Eight bits therefore correspond to two digits. The first digit represents groups of 16; the second is the remainder.

3. Understand and complete the hexadecimal output
Decimal uGroups of 16 and remainderHex result
50 × 16 + 505
1288 × 16 + 080
25515 × 16 + 15; hexadecimal 15 is FFF

Where: PROJECT/lab.js, function toHex8(u). Keep validateByte(u) and replace only that function’s return null;. Do not replace another TODO or paste JavaScript into the terminal.

Paste into: PROJECT/lab.js · replace return null inside toHex8(u)

return u.toString(16).padStart(2, '0').toUpperCase();

The three operations have separate purposes: toString(16) converts to base 16; padStart(2, '0') preserves the two-character width; toUpperCase() changes letters such as ff to FF. This is presentation of the same number, not a change to its value.

Do: save, reload index.html and try 5 and 255. Check: 05 and FF. If you see only 5, conversion works but the width requirement is still unmet.

Use the S05 prompt if you want help distinguishing Git states or explaining the conversion. Check the answer with the application and reference. Gemini is optional in this seminar and unavailable during Q05.

4. Check the result and read the difference

Where: the test page, VS Code Source Control and your short project notes. Reload PROJECT/tests.html, select S05 and click Run. This stage includes the earlier checks and the hexadecimal checks. The same Run action also reads every entry in PROJECT/custom-tests.js and lists its result with the other checks.

Check: the S05 required checks pass, including the row checking all 256 valid hexadecimal results. This finite-domain check is possible because the input range is small. It checks behaviour against the specification; it does not establish who wrote the code.

  1. Open Source Control in VS Code and select PROJECT/lab.js to inspect the difference. You should see a change inside toHex8, not a replacement of the whole project.
  2. In PROJECT/evidence.md, record a prediction, its actual result and the S05 test result. Add a short resumption note with your repository URL, local folder, last completed stage and first next action.
  3. In PROJECT/README.md, record that S05 hexadecimal output is complete and how to open the application and tests.
Optional extra test for the leading zero

You may add this to the existing array in PROJECT/custom-tests.js. It is optional in S05. Keep the existing entry, add a comma between objects and preserve the array brackets.

Paste into: PROJECT/custom-tests.js · an additional object in CustomTests

{label: 'Hex width at 5', input: 5, operation: 'hex', expected: '05'}

Save and reload the test page. The custom test must compare with the string '05', not the number 5. Its expected value comes from the requirement, rather than copying the current output.

Why inspect both tests and the difference? Tests check selected behaviour; the difference shows exactly which content you are about to preserve. A green test result cannot show an unrelated accidental edit.

5. Save, select, commit and push

These are different actions. Save writes the file locally. Stage selects content for a commit. Commit records a local version. Push sends that version to GitHub. Skipping push leaves the latest commit only on your computer.

Where: Source Control in VS Code or its terminal at the repository root. Save all edited files. Select the intended files for staging, read the staged difference and commit with a short message that describes the result. Then push to your own origin.

Command route for the same actions

The optional custom-test file can remain unchanged; adding it here will not manufacture a change.

Paste into: VS Code terminal · repository root

git status
git add PROJECT/lab.js PROJECT/README.md PROJECT/evidence.md PROJECT/custom-tests.js
git diff --cached
git commit -m "S05: complete two-character hexadecimal output"
git push origin main
git status

Check locally: the commit appears in history and git status reports no pending changes. Check remotely: open your own GitHub repository, check the latest commit message and open PROJECT/lab.js to see the new hexadecimal line.

Why both checks? A clean local working tree says the edits are committed. It does not by itself say they were published. GitHub should show the version you intend to resume.

“Nothing to commit” or a rejected push

If there is nothing to commit, check whether you saved and staged the intended change or already committed it. If push is rejected, read the account, remote URL and reason before trying again. Do not create a second repository, discard work or force-push as a quick fix. Keep the useful work and ask us to inspect the actual state.

6. Confirm where you will resume

At minutes 70–75, read your resumption note in evidence.md. It should identify your own repository URL, the local folder, S05 as the completed stage, the test result and the first next action: investigate signed interpretation in S06.

Try explaining to yourself which browser tab runs the project and which tab shows GitHub source. If you add a missing note now, save, commit and push that documentation too. Do not copy a “final SHA” into the project file; the final version will be identified in Moodle during S07.

7. Q05 and the idea to keep

At minutes 75–85, open Q05 in our Moodle course. It lasts 10 minutes and contributes at most 0.20 real points. Work individually without Gemini, other AI or classmates. The shared reference is permitted.

The practical work gives you concrete examples for the quiz: why a byte uses eight bits and two hexadecimal characters, which input is valid and where work exists after save, commit or push. You need to understand these relationships, not memorise a long list of clicks.

What remains useful: before changing a project, run its current behaviour; before publishing, inspect what changed; before leaving it, write where to resume. Continue with S06 in the same repository.
