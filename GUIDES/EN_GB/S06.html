S06 · Investigate, test and repair

Keep your own hypothesis, check an AI claim and integrate a repair supported by boundary tests.

Today’s question and result

A program gives the right answer for 0 and 255. Is that enough to trust every value between them? Today we investigate the declared defect in asSigned8(u). The stored eight-bit pattern can be right while its signed interpretation is wrong.

You will preserve your own hypothesis before asking Gemini or reading the fallback, choose one precise claim to test and publish a repair. Your issue records the problem, the branch holds the change and your own pull request explains why it should enter main.

A wrong initial hypothesis is acceptable. Keep it and show how the evidence led you to keep or revise the explanation. The aim is an investigation you can justify.

2. Calculate the expected interpretation, then reproduce the defect

In an unsigned byte the leftmost bit has weight 128. In eight-bit two’s complement it has weight −128; the other seven weights remain 64, 32, 16, 8, 4, 2, 1. The pattern is unchanged; its interpretation changes.

Thus 01111111 is 127 in either interpretation. 10000000 is unsigned 128 but signed −128. 10000001 is −128 + 1 = −127. 11111111 is −128 + 127 = −1. Equivalently, subtract 256 for unsigned values from 128 through 255 inclusive.

The branch already exists or the custom file no longer loads

If the branch exists from your own earlier attempt, inspect it before using git switch fix/signed-boundary. Do not delete it just because the name exists. The expected signed value is the number -128, not a copied actual value.

Why do several checks fail for the same defect?

With S05 hexadecimal conversion completed, S06 detects the defect in two supplied checks: the individual case for 128 and the check of all 256 signed values. Adding your own test for 128 produces a third failure. The same incorrect input has been detected through three checks.

Custom tests run under every selected stage. After adding the signed test, S05 also reports it as failed until the fix. The S05 check at the start took place before you added this test. Keep the test; after the fix it should pass. Other tests you add may change the result count.

6. Make the smallest justified repair

Where: PROJECT/lab.js, function asSigned8(u). Compare the condition with the mathematical cases: unsigned values below 128 retain their value; values at or above 128 subtract 256.

  1. Find the condition that chooses between those cases.
  2. Correct its treatment of the exact boundary. Keep validateByte(u) and the other functions.
  3. Save and reload the application. Rerun 127, 128, 129 and 255.
  4. Reload the test page, select S06 and run it again.
  5. Update your evidence with the actual results and conclusion. In README, record that the signed interpretation stage is complete and identify S07 as the next action.

Check: 128 now gives −128; the neighbouring cases stay correct. S06 required checks and your custom boundary test pass. Parity remains unfinished.

Hint after your hypothesis and test are recorded

The starter condition is u > 128. Ask whether 128 should be treated with 127 or with 129 according to the definition. The distinction between > and >= decides which case includes the boundary.

Why rerun neighbouring values? A repair should correct the counterexample while preserving results that already worked. Those are regression checks. The full-domain row is additional evidence because this domain contains only 256 valid values.
